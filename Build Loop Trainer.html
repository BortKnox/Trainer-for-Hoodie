STAGE 01 / ORIENTATION

One team. Clear boundaries.

The loop works because each tool has a defined job, the hand-off is explicit, and nothing is accepted just because an AI says it is finished.

START HERE · 5 MIN

The decision-maker

DEEPSEEK · ARCHITECT / FOREMAN

The planner

MANUS · BUILDER / OPERATOR

The implementer

Uses its available workspace and approved connectors to inspect, edit, run checks, and report. It follows the approved ticket; it does not redesign the project mid-task.

Stores the code, commits, branches, issues, and review history. A chat transcript is not a substitute for a reproducible project history.

The governing rule: one approved objective per loop. If the implementation reveals a new requirement, stop, report it, and ask for a revised ticket. Do not let a small task become an unreviewed rewrite.

Three non-negotiable rules

Vocabulary: a repo is the project folder tracked by Git; a commit is a named snapshot of changes; a branch is an isolated line of work; a diff shows exactly what changed; an acceptance criterion is a testable condition that proves the task is done.

WORKING RULES
- First confirm the repository, current branch, and working-tree state. Do not overwrite uncommitted user work.
- If repository state or ticket assumptions do not match reality, STOP and report the discrepancy before editing.
- Follow the approved file scope. Inspect relevant code before changing it.
- Make the smallest maintainable change. Preserve existing architecture, naming, formatting, and behaviour outside scope.
- Do not add dependencies, change credentials, alter deployment/release settings, delete data, or perform external/destructive actions unless explicitly authorised in the ticket and separately confirmed by the user.
- Do not claim a test passed unless you ran it and can report the actual output. If a test cannot run, explain why and provide the manual alternative.

STAGE 05 / VERIFY
Trust the evidence, not the completion message.
A task is not done because the builder says “completed”. It is done when the change matches the brief, the relevant checks pass, and you can explain what changed.
HUMAN QUALITY GATE


Inspect the diff
Review every changed file. Look for unrelated edits, hard-coded secrets, debug leftovers, accidental formatting churn, unexpected dependencies, and changes to configuration or data.
Re-run important checks
Where practical, verify critical tests yourself or ask for reproducible commands. Test the actual user-facing behaviour, not just whether the application launches.


Acceptance review









Reject or pause if tests were not run, the diff is broader than agreed, the builder cannot explain a change, or any high-risk action happened without approval. Ask for a correction ticket; do not patch around uncertainty.




ACCEPT
Ready to record
Scope matches, evidence is sufficient, tests pass, and no unresolved critical issue remains.
REJECT / REVISE
Return with evidence
Identify the failed criterion and provide the smallest reproducible example. Ask for a new bounded ticket.

FIELD GUIDE / QUICK REFERENCE
When the loop gets messy.
Use these recovery patterns rather than letting the agents improvise. Keep the current task safe, small, and observable.
REFERENCE


Manus says it cannot access the repository
Check that the correct GitHub account is connected, the intended repository is selected, and the connector permission covers the requested operation. Ask Manus to report the exact access failure. Do not paste a personal access token into chat as a workaround.


DeepSeek proposes a large rewrite
Ask it to identify the minimum change that satisfies the acceptance criteria. Require a list of files to change and explicitly exclude unrelated refactors. Split the work into sequential tickets; approve only the first.


Manus changed files outside the ticket
Pause. Do not merge or release. Inspect the diff, identify unrelated changes, and request a clean revision or revert on a safe branch. Update the ticket with an explicit file boundary.


Tests fail or cannot run
Record the exact command and output. Separate a product defect from a missing dependency, environment issue, or unsupported test. Ask for a minimal diagnosis; do not accept a claimed pass without evidence.


The builder says it is finished but provides no proof
Ask for the changed-file list, diff/commit reference, exact checks executed, actual results, acceptance-criteria status, and known limitations. If it cannot provide them, treat the task as unverified.


The task reveals a new requirement
Stop implementation and return to the architect stage. Capture the new requirement in the brief, revise scope and acceptance criteria, and obtain approval for a new ticket.


Credits or usage are limited
Use DeepSeek to prepare a concise, complete ticket before invoking Manus. Avoid repeated broad scans; provide a focused file tree and relevant source files. Ask Manus to perform one task and one verification pass. Check the current plan's usage and pricing in the product itself—limits can change.


Short correction prompts


ARCHITECT REVISION
Revise the plan to the smallest change that satisfies the original outcome. Remove optional improvements and unrelated refactors. State exact files in scope, explicit exclusions, acceptance criteria, tests, and rollback. Do not implement. Identify any unknowns that block safe work.


BUILDER STOP / REPORT
Stop making changes now. Do not commit, merge, release, or perform further actions. Report the current repository and branch, working-tree state, every file changed, what has and has not been tested, any partial work, and the safest recovery options. Preserve user work; do not discard changes without explicit approval.
